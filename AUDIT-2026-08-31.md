### 2.2 The test suite could not pass with the configuration it ships with (P0)

`phpunit.xml` sets `DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`. The Phase 4.3+ suites
deliberately use `DatabaseTruncation` instead of `RefreshDatabase` (a purchase refuses to
run inside a transaction it does not own). `DatabaseTruncation` truncates but **never
migrates**, and an in-memory database does not survive the per-test application refresh.
Result on a clean checkout: **211 errors**, all of the form
`SQLSTATE[HY000]: General error: 1 no such table: ledger_accounts`.

The phase reports never saw this because they exported `DB_CONNECTION=mysql … DB_DATABASE=thai_lottery_test`
into the shell, which overrides the `<env>` defaults.

**Fixed** in three coordinated places:

- `phpunit.xml` — the default test database is now the file-backed
  `database/thai_lottery_test` (the name every suite's fail-safe guard already allows), and
  it is git-ignored.
- `tests/TestCase.php` — `createApplication()` now migrates that database once per PHPUnit
  process if it is empty, **before** the traits run, and refuses to migrate any database
  whose name is not `thai_lottery_test` or `:memory:`. On an already-migrated MariaDB test
  database it is a no-op, so the historical workflow is unchanged.
- `phpunit.xml` — `FILESYSTEM_DISK` was `array`, which is **not a configured disk** in
  `config/filesystems.php`; any `Storage` call in a test would have failed with
  *"Disk [array] does not have a configured driver"*. Now `local`.

### 2.3 Four atomicity tests were MySQL-only (P1)

`BetPurchaseAtomicityTest::assertRollsBackWhenStepFails()` injects a failure with
`CREATE TRIGGER … SIGNAL SQLSTATE '45000'`. SQLite has no `SIGNAL`, so all four rollback
tests errored with `near "SIGNAL": syntax error` on the configured default database.

**Fixed:** the injection is now written in the dialect of the live connection —
`SIGNAL` on MySQL/MariaDB, `RAISE(ABORT, …)` on SQLite — and skips with an explicit message
on any other driver. The assertion being made is identical on both.

### 2.4 Eight settlement tests asserted the database driver's formatting, not the project's money rule (P1)

They read money with the **raw** query builder (`DB::table('bet_items')->value('actual_payout')`),
which bypasses the model's `decimal:2` cast, then compared with `assertSame('9000.00', …)`.
MySQL returns `'9000.00'` for a `decimal(20,2)` column; SQLite's NUMERIC affinity returns
`'9000'`. The stored amount is identical — the assertion was pinning driver behaviour.

**Fixed:** a new `Tests\TestCase::assertStoredMoneySame()` compares with `bccomp` at scale 2
(the project's own money rule) and still asserts the value is a plain decimal string. The
eight call sites now use it. Assertions about *format* (`/^[0-9]+\.[0-9]{2}$/` on the
service's own output) were left untouched, because there the format is the requirement.

### 2.5 One config test failed on a supported PHP version (P2)

`DatabaseDriverOptionsTest::the_modern_and_legacy_ssl_ca_attribute_ids_are_identical`
asserted `class_exists(\Pdo\Mysql::class)`. That class only exists on **PHP 8.4+**, while
`composer.json` requires `php: ^8.2`. On 8.2/8.3 the project deliberately uses the legacy
`PDO::MYSQL_ATTR_SSL_CA` fallback, so the test reported a supported runtime as a defect.

**Fixed:** it now skips with a message that states why, and the sibling tests continue to
pin the fallback path.

### 2.6 The API had no way to authenticate (P0, functional)

Every route added in Phase 4.4 sits behind `auth:sanctum`, and the project shipped **no
endpoint that issues a token**. The only way to obtain a credential was `php artisan tinker`
on the server, so the whole HTTP surface was unreachable by any real client, and the
`login` rate-limit ceilings already declared in `config/security.php` were read by nothing.

**Added** (built only on mechanisms already present — Sanctum, `personal_access_tokens`,
`HasApiTokens`, the `active` middleware, `audit_logs`, `AuditAction::Login/Logout/LoginFailed`,
and the existing `ApiResponse` envelope):

| Route | Middleware | Notes |
|---|---|---|
| `POST /api/v1/auth/login` | `throttle:login` | The only public route in the file |
| `GET /api/v1/auth/me` | `auth:sanctum`, `throttle:api`, `active` | Identity only — no balance, no wallet id |
| `POST /api/v1/auth/logout` | `auth:sanctum`, `throttle:api` | Revokes **only** the presented token |

Security properties, each pinned by a test:

- Unknown account, wrong password and suspended account return a **byte-for-byte identical**
  401 `unauthenticated` body, so the endpoint is not an account-enumeration oracle. The real
  reason goes to `audit_logs` (`no_such_account` / `bad_password` / `inactive_account`).
- A dummy `Hash::check` runs when no account matched, so response time does not leak
  existence.
- `throttle:login` is registered from `config('security.rate_limits.login')` and keyed on
  **both** the hashed identifier and the client IP, exactly as that config's
  `by => 'email_and_ip'` specified.
- Sign-in accepts either the `email` or the `username` unique column; the value is never
  interpolated into SQL.
- The response body contains no password, no hash and no token beyond the one just issued;
  the identity payload is a hand-written whitelist of 7 fields.
- 12 new tests (`tests/Feature/Api/V1/AuthApiTest.php`).

### 2.8 `phpunit.xml` shipped an APP_KEY that is not a valid key (P0 for any HTTP test)

`phpunit.xml` set `APP_KEY` to a `base64:` string that does not decode to 32 bytes. Any
test that resolves the encrypter — which means any HTTP test carrying a session — died with
`RuntimeException: Unsupported cipher or incorrect key length`.

This had never been caught because none of the 315 pre-existing tests made a
session-bearing HTTP request: they are unit and console tests, so the encrypter was never
resolved and the broken key was never read. The first admin-panel test found it on its
first run, and it would have hit the first developer to add any HTTP feature test.

**Resolution:** replaced with a freshly generated valid 32-byte key. One line, large blast
radius.

### 2.9 The chart of accounts was never seeded — a fresh install could not take a deposit (P0)

`WalletService` declares eight ledger account codes as constants — 1000 System Cash, 1100
Withdrawal Clearing, 2000 Player Balances, 3000 Manual Adjustments, 4000 Bet Revenue, 4100
Fee Revenue, 5000 Prize Expense, 5100 Agent Commission — and
`LedgerPostingService::resolveAccount()` throws `ledger_account_missing` when a code has no
row. Its own error message reads *"Seed the chart of accounts before posting financial
transactions."*

Nothing seeded them. `DatabaseSeeder` called only `RolePermissionSeeder`, no migration
inserted the rows, and no `LedgerAccountSeeder` existed. The eight codes were PHP constants
and never data.

**Consequence:** a fresh install could migrate cleanly, seed roles, register a player, and
then fail on the first deposit with what reads to an operator as an internal error. Every
financial path in the application was blocked on missing reference data, on every new
environment.

**Resolution:** `database/seeders/LedgerAccountSeeder.php`, registered in `DatabaseSeeder`.
It is keyed on the `WalletService::ACCOUNT_*` constants rather than literal strings, so the
codes the application posts to and the codes the database holds cannot drift. It is
idempotent, and it deliberately never writes `opening_balance` or `current_balance` on an
existing row — those are posting-derived state, and a seeder that reset them would destroy
the audit position of a live ledger. `tests/Feature/Seeders/LedgerAccountSeederTest.php`
(7 tests) reads the constants by reflection rather than from a hand-written list, so a ninth
account code added later cannot silently go unseeded.

## 3. Gaps: what is not built (not defects — unbuilt scope)

### 3.1 The system could not run itself — **now fixed**

*Original finding:* `routes/console.php` registered exactly one command — Laravel's
`inspire` — and `bootstrap/app.php` declared **no schedule**. There were no
`app/Console/Commands`, no `app/Jobs`, no `app/Events`, no `app/Listeners`. So although
`DrawLifecycleService`, `DrawResultPublicationService` and
`DrawSettlementSimulationService` were complete and tested, **nothing called them**: draws
were never created on the 1st/16th schedule that `config('lottery.draw.official_schedule')`
declares, never auto-closed the 5 minutes before the draw that
`config('lottery.closing.auto_close')` declares, and never settled.

*Resolution:* the draw lifecycle is now automated. `bootstrap/app.php` registers a single
scheduled orchestrator, `lottery:tick`, which runs five commands in order every minute —
provision → open → close → mark result-pending → settle — each of which also runs
standalone with `--dry-run` and `--force`. A new `DrawScheduleService` owns the calendar
arithmetic (and only that: it never writes `draws.status`, never publishes, never moves
money). See `PHASE-AUTOMATION-REPORT.md` and the README's "Draw automation" section.

Two things are still deliberately **not** automated, and tests enforce it: **result
publication**, because the official numbers come from the Thai Government Lottery Office
and a human must enter them (`lottery:publish-result`), and anything financial — no
scheduled task writes `payouts`, `deposits`, `withdrawals` or `ledger_entries`.

Still unbuilt in this area: a queue connection and a mail transport remain configured and
unused (no jobs, no notifications), and there is no supervisor/systemd config for
`schedule:run` in the repository.

### 3.2 Admin had no surface at all — **now largely fixed**

*Original finding:* no `app/Filament`, no admin panel package in `composer.json`, no admin
route, no admin controller, no Blade view, no policy wired to an operator screen. Every
operator action the domain supported — approving a deposit, approving a withdrawal, setting
a number limit, publishing a result, reading the audit trail — was reachable only from code.
The five roles the seeder creates (`super-admin`, `admin`, `agent`, `player`, `auditor`) and
the permissions `manage system settings`, `view audit logs`, `view financial reports`,
`reconcile ledger` had no surface to act on.

*Resolution:* there is now a Filament 3 operations panel at `/admin` — 30 of the
application's 48 routes, 53 files under `app/Filament`, 13 resources across five navigation
groups (Lottery, Finance, Risk, People, Compliance), an operations dashboard with four
widgets, and 166 new tests.

The governing decision is that **the panel never writes state a domain service owns**. It
only decides which buttons to offer; every action calls the service that already owns the
transition and reports what it said. An operator acting on a stale screen gets the service's
own refusal as a red notification and nothing is written. Draw publication, settlement,
deposit and withdrawal decisions, wallet locks and adjustments, and number-limit
configuration all go through their existing services.

Authorization is a single surface, `App\Support\Admin\AdminAccess`, which reads the seeded
permission phrases. It does **not** use the model policies, for the reason in §2 and §3.2.1
below. Panel entry requires an `Active` account, one of `super-admin`/`admin`/`auditor`, and
`view dashboard`; everything else is a 403.

Read-only is the default where records represent something that already happened: bets,
tickets, financial transactions, ledger accounts and agents have no write path, and audit
logs cannot be edited or deleted by anyone, super-admin included, with tests proving it.

Two Blade views are overridden under `resources/views/vendor/` because upstream Filament
renders record counts through `Illuminate\Support\Number::format`, which hard-requires
ext-intl and turns a missing optional extension into a 500 on every paginated table. They
are pinned to Filament 3.3 and create a re-copy obligation on upgrade. See
`PHASE-6-ADMIN-REPORT.md` §4.1 and the README.

Still unbuilt in this area, and the reason module 6 scores 70% rather than higher: no system
settings page (`manage system settings` still grants nothing), no financial reporting or
export, no ledger reconciliation workflow beyond a balance check widget, no agent commission
management, no reversal path for a confirmed deposit or completed withdrawal, no panel-side
two-factor authentication or impersonation, and no bulk actions anywhere (the last is
deliberate — every financial decision is one record at a time).

One gap forced a compromise worth naming: **no service owns user status transitions**, and
`UserStatus` has no transition graph. `UserResource`'s status actions are therefore the one
place in the panel that writes domain state directly. It is explicit, guarded, audited and
commented as such, and the recommended fix is an `App\Services\Identity\UserModerationService`.

#### 3.2.1 Why the panel does not authorize on policies

`App\Policies\BasePolicy` builds ability strings like `draw.view`, while
`config/permission.php` and `RolePermissionSeeder` seed phrases like `view draws`. The two
vocabularies never meet, so every policy derived from `BasePolicy` — Wallet, LedgerEntry,
Bet, Ticket, Draw, Payment, Agent — resolves false for every role except `super-admin`,
which passes only through the `Gate::before` bypass in `AuthServiceProvider`.

Building the panel on that layer would have produced a panel where admins see nothing and
super-admins see everything, regardless of the seeder. This defect is **pre-existing and
still unfixed**: repairing it means choosing which vocabulary is canonical, migrating the
other, and re-testing every policy. It is its own piece of work, not a rider on a panel
phase.

## 4. The measured gap

Completion is scored per module from what is actually on disk (files, routes, tests), and
weighted by the share of the total build each module represents.

| Module | Weight | Built | Gap | Change this phase |
|---|---|---|---|---|
| 1 — Core architecture (schema, enums, models, policies, config) | 10% | 100% | 0% | — |
| 2 — Wallet + double-entry ledger | 12% | 80% | 20% | was 70% — the ledger now has an operator surface (wallets, transactions, chart of accounts) and a seeded chart of accounts |
| 3 — Risk + number limits | 8% | 95% | 5% | was 85% — number limits are now configurable by a risk officer |
| 4 — Betting engine + purchase API + token surface | 15% | 92% | 8% | — |
| 5 — Draw, result, settlement (5.2 real payout absent) | 10% | 65% | 35% | was 60% — publication and settlement now have a human surface |
| 6 — **Admin panel** | 12% | **70%** | **30%** | **was 0%** |
| 7 — Frontend (asset stubs only, no views or web routes) | 15% | 5% | 95% | — |
| 8 — Real-time draw feed | 5% | 0% | 100% | — |
| 9 — Payment gateways + agent system | 8% | 15% | 85% | was 10% — agents and commissions are readable |
| 10 — Security, testing, automation, deployment | 5% | 72% | 28% | was 70% — two P0 defects fixed, 168 tests added |
| **Overall** | **100%** | **≈61%** | **≈39%** | was ≈53% / ≈47% |

The weighted sum is 61.45, rounded to ≈61%.

**Why module 6 is 70% and not higher.** The operator surface for the features that exist is
built and tested: draws, results, settlement, deposits, withdrawals, wallets, number limits,
users, roles, and an append-only audit trail. What is missing is the management layer above
it — a system settings page (`manage system settings` still grants nothing), financial
reporting and export, a ledger reconciliation workflow rather than a balance-check widget,
agent commission management, real-payout operations, and panel-side two-factor
authentication and impersonation. Several of those are blocked on services that do not
exist rather than on panel work; see `PHASE-6-ADMIN-REPORT.md` §6.

Read plainly:

- **Admin page: 30% gap** — an operations panel exists and is the way the money and risk
  features are now driven. It cannot yet change a setting, produce a report, or reverse a
  financial decision. It was a 100% gap before this phase.
- **Player-facing product: ~95% gap** — the backend can take a bet over the API, but there
  is still no page, no wallet endpoint and no live result feed. This is now the largest
  remaining gap by weight.
- **Domain/backend core (modules 1–5): ~15% gap**, and most of what remains is Phase 5.2
  real-money settlement, which was excluded on purpose.
- **Whole system: ~61% built, ~39% gap** (was ~53/47 before the admin panel landed).

The 5 skips are honest and each states its reason: 1 requires PHP 8.4 (`Pdo\Mysql`) and
4 are multi-process concurrency probes (`SELECT … FOR UPDATE` race conditions) that need a
server-based database, so they cannot run on the SQLite default. The phase reports state these ran green on
MariaDB with PHP 8.5; that environment was not available here, so treat it as their claim
rather than something this audit re-verified.

The suite is **not safe to run concurrently against one SQLite file**: parallel phpunit
processes corrupted `database/thai_lottery_test` repeatedly during this phase
(`database is locked`, `database disk image is malformed`). The figures above are from a
single serial run against a freshly created file.

`composer audit` reports 3 `laravel/framework` advisories — CRLF injection in the email
validation rule, and temporary signed URL path confusion — because the project pins
`laravel/framework ^11`. No phase has changed that constraint; it is a dependency-policy
decision for the owner.

## 6. Recommended order for the remaining ~39%

1. ~~**Automation** — console commands + schedule for open/close/settle.~~ **Done** —
   see §3.1 and `PHASE-AUTOMATION-REPORT.md`.
2. ~~**Admin panel (Phase 6)** — the largest single gap and the only way to operate the
   money and risk features that already exist.~~ **Done** — see §3.2 and

   `resources/views` is empty and `routes/web.php` is a placeholder, so `/` returns 404 and
   the six JS modules and two CSS files have no page to load them.
4. **Wallet + deposit/withdrawal HTTP surface** — the domain and the operator screens both
   exist; players still have no endpoint to see a balance or request a deposit.
5. **Repair the two domain inconsistencies this phase documented**, both small and both
   currently worked around rather than fixed: the `BasePolicy` ability-vocabulary mismatch
   (§3.2.1), and `BetType::digits()` returning 2 for `Tod` and `Run` where config says 3
   and 1.
6. **Fill the services the panel had to work around**: `UserModerationService` for user
   status transitions, a real `AuditRecorder`, `canMarkProcessing()` on both approval
   services, and an agent commission service.
7. **Phase 5.2** real-money payout settlement, if the product is ever to move real money.
8. **Real-time (Phase 8)**, then **gateways/agent (Phase 9)**, then **CI/deploy (Phase 10)**.
